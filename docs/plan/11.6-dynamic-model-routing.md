# Step 11.6: Dynamic Model Routing via User Event Context

**Agent:** architect (design) -> implementer (code)
**Depends on:** step 07 (protocols split), step 05 (ModelBundle enforcement)

## Problem

Currently the pipeline has two major UX issues:

1. **Model name is static per pipeline.** `ClientPreprocessorNode` takes `model_name` as a constructor arg and bakes it into every `TritonRequest`. A user processor cannot route different events to different Triton models (e.g., yolo11s vs yolo26l) based on event content. To support multi-model routing, the user event context must be able to carry `model_name` / `model_version` / task type, and shipped processors must read it.

2. **One RedisStreamSource per event type.** `LiveRedisStreamSource[T]` is generic over a single event model `T` and reads one stream. Users must manually instantiate a separate source for every event type they handle. Instead, a single unified source class should exist that the user only needs to **type-annotate** — no manual Redis wiring, no constructor args for stream names.

## Design

### 11.6.1 Add `InferenceTarget` mixin for user events

Create a protocol / mixin that user events can implement to carry per-event inference routing info:

**File:** `engine/events.py`

```python
class InferenceTarget(BaseModel):
    """Mixin for user events that carry per-event model routing info.
    
    When present on the context event, shipped preprocessor nodes
    read model_name/model_version from the event instead of using
    their constructor defaults.
    """
    model_config = ConfigDict(frozen=True)
    
    target_model: str = ""
    target_model_version: str = ""
```

User events that want dynamic routing inherit from both `Event` and `InferenceTarget`:

```python
class MyEvent(Event, InferenceTarget):
    image_path: str
    task_type: str = "detection"
```

Events that don't inherit `InferenceTarget` keep the current static behavior — full backward compatibility.

### 11.6.2 Update `ClientPreprocessorNode` to respect `InferenceTarget`

**File:** `engine/shipped_processors.py`

In `ClientPreprocessorNode.__call__`, after getting `event.context`, check if context is `InferenceTarget`. If so and `target_model` is non-empty, use it instead of `self._model_name`:

```python
model = self._model_name
version = ""
if isinstance(event.context, InferenceTarget):
    if event.context.target_model:
        model = event.context.target_model
    if event.context.target_model_version:
        version = event.context.target_model_version

triton_req = TritonRequest(
    model_name=model,
    model_version=version,
    raw_image=tensor,
    input_name=self._input_name,
    output_names=self._output_names,
)
```

Constructor `model_name` becomes the **default** — overridden per-event when `InferenceTarget` is present.

### 11.6.3 Unified Redis source — type-annotation-driven

Replace the pattern where users manually create `LiveRedisStreamSource[MyEvent]` with constructor args. Instead, provide a base class that only needs a type annotation:

**File:** `connectors/redis_stream.py` (or new `connectors/auto_source.py`)

```python
class AutoRedisSource[T: Event](BaseThreadSource[T | ConnectorError]):
    """Redis stream source that derives stream name from config + event type.
    
    Users subclass with a type annotation only — no constructor override needed:
    
        class MySource(AutoRedisSource[MyEvent]): ...
    
    Stream name, consumer group, and all Redis params come from AppConfig.source.
    The event model T is extracted from the generic parameter at registration time.
    """
```

Key behavior:
- Stream name comes from `AppConfig.source.stream_name` (single config field)
- Event model `T` is extracted from generic param via `__orig_bases__` (same mechanism `PipelineRegistry` already uses)
- Redis client and config injected by `Application.build()` or DI provider — not by user
- User code is just: `class MySource(AutoRedisSource[MyEvent]): ...` — one line

### 11.6.4 Update `ModelBundle` to accept optional model routing

`ModelBundle` currently takes a fixed preprocessor. For dynamic routing, the bundle's preprocessor should work with any model when `InferenceTarget` is on the event. No changes to `ModelBundle` dataclass itself — the preprocessor inside it just becomes model-aware via 11.6.2.

Document that when using `InferenceTarget` events, the `model_name` in `ClientPreprocessorNode` constructor serves as the **fallback default**, not the only option.

### 11.6.5 Update application construction in `main.py`

**Note:** `providers/app_factory.py` was deleted in step 02.7 (DI removal). Application is constructed manually in `main.py`.

Update `main.py` to:
- Accept an optional `source_type` parameter for `AutoRedisSource[T]` subclass
- If provided, instantiate it with Redis client + config
- If not provided, fall back to current `LiveRedisStreamSource` behavior

## Constraints

- **Full backward compatibility.** Existing code that doesn't use `InferenceTarget` or `AutoRedisSource` must work unchanged.
- **No class paths in config.** The event type comes from Python type annotation, not a config string.
- **isinstance check is acceptable** for `InferenceTarget` — it's a pydantic BaseModel, not a Protocol, and the check is in a single hot path (preprocessor node).
- **No new dependencies.** Everything uses existing pydantic + typing machinery.

## Non-goals

- Multi-stream multiplexing (reading from N streams in one source) — out of scope. One source = one stream.
- Automatic postprocessor selection based on model — user handles this in their postprocessor or via separate bundles.
